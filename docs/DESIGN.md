# Design

A `.w3g` replay holds player inputs and almost nothing else. WC3V simulates
enough of Warcraft III to turn those inputs into a match you can read: who
built what, where the heroes went, which camps died, when the game turned.

## What a replay contains

A timestamped stream of actions, one per command a player issued, plus the
commands the game issues on their behalf. Metadata covers the map and the
players. Not in the file: starting positions, unit deaths, item drops, creep
kills, gold. All of that is state the game computed and never wrote down, so
the engine has to derive it deterministically from the stream, in order.

## Unit identity

Two id pairs describe a unit:

- `itemId1 + itemId2` is the type (a Footman, a Farm).
- `objectId1 + objectId2` is the instance.

A `Change Selection` action carries the instance ids of the selected units. A
`Select Subgroup` action carries both pairs for the unit that leads the group.
A unit is **registered** once it has been the lead of a subgroup, because that
is the first moment the two pairs are seen together.

Object ids are handed out by an incrementing counter, so a player's starting
workers and town hall sit inside a known span. That span lets the engine name
an unregistered unit with reasonable confidence.

## Backfilling

Actions issued to a unit before it is registered are stored against its
instance ids with the game time. When the unit registers, the stored actions
are replayed through the same simulation the registered path uses, so a ghoul
that creeped for two minutes before its first direct click still gets its
walk. `test-backfill.w3g` is the reference case.

## Abilities and levels

Ability actions come in four shapes: no target, a point target, a target with
an object id, and two targets. `GiveOrDropItem` is the fifth active command.
A hero's level is inferred from the action that spends a skill point, so it
lands at the moment the player chose the skill rather than at the level-up.

## Starting positions

The map seed is not recoverable. Starting locations come from the map's
scripts, and the player's position is the one nearest their first buildings,
with positions already taken by other players ruled out.

## Replay quirks handled

- Duplicated actions in laggy games. Shop cooldowns stop a hero buying an item twice.
- Summons the player never clicks. A snapshot at summon time is matched by spawn time when a destroy call finds no registered unit.
- The "same block" flag on selection changes is consistent enough to prune units tracked too long, such as dead ones.
- Item moves carry a target coordinate; a non-zero decimal part means the item came from a shop.

`parseConfidence` counts how often the engine met something it could not
place. Output is always produced; the number says how much to trust it.

## Race build mechanics

`BuildMechanic` in `helpers/mappings.js`, chosen per race and building:

| Race | Mechanic |
|---|---|
| Orc | peon enters the building, released on completion |
| Undead | acolyte summons the building and is free at once |
| Night Elf, ancient | wisp is consumed, food drops by one |
| Night Elf, other | wisp is consumed for the build and released |
| Human | peasant works on site, can be pulled, several can share |

All timed events run on `EventTimer`, never on `setTimeout`. Undead lumber
is `workers.ghoulsOnLumber`, separate from `workers.onLumber`.

## Research

`helpers/researchMeta.json` covers the upgrades of every race, generated by
`tools/parse-upgrade-data.js`. In W3Champions and FLO replays research
arrives on the `TrainUnit` flag, so building dispatch checks `researchMeta`
before treating an item as a unit.

## Expansions

A town hall placed more than 2500 units from the starting position is an
expansion, flagged in `Player.addPlayerBuilding()`.

## Validation

`lib/ReplayValidator.js` runs after the parse and writes a `validation` key
only when it finds something: a building or unit ahead of the tier the player
is known to have, or missing worker data. W3Champions replays lack action
`0x10`, so tier upgrades there are detected from the building's item id
changing in `Player.selectSubgroup()`.

## Maps

`tools/data-tool.js` extracts pathing, doodads, neutral buildings and terrain
from `.w3x` files into `mapdata/`, and the client cache under `client/maps/`
is generated from that. Creep camps within 1500 units of an unused starting
slot are dropped from the output. `helpers/mapResolver.js` is the only place
a replay's map name is resolved; names nest (Echo Isles inside Echo Isles S2)
and a first-match lookup silently reads the wrong map.

## In-browser parsing

`tools/build-parser-bundle.js` browserifies the same engine into
`client/js/vendor/wc3v-parser.bundle.js`. The site parses in a Web Worker and
stores results in IndexedDB. Rebuild the bundle after any change to `lib/` or
`helpers/`, or the site and the desktop app keep running the old parser.

## Compare to pro

`SummaryExtract` reduces a parse to race, matchup, opener, key units, map and
length. `CompareMatcher` scores the pro library against it. `ReplayAnalyzer`
grades macro, production, item economy and idle resources, with timestamped
findings. `CompareCharts` draws the curves. Categories that do not compare
(different race composition) say so instead of scoring.
